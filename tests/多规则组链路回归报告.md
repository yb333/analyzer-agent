## 二、发现的 3 个真实 BUG（均已修复）

> 每个 bug 都通过独立的探测脚本实测复现，确认根因后修复。

### BUG 1：多目标规则组依赖漏建（最严重）

**现象**：一个规则组内多步写多张表（step1 写 mid_x、step2 写 final_x），当下游规则组读取其**早期步骤**写的 mid_x 时，merge 阶段依赖建立失败，导致下游 exec_sequence 没排在上游之后 → **步骤顺序错乱**。

**根因**：`merge_rule_groups` 的 `group_target` 用 `dict[dir]→单个 target`，只记录 `max(exec_sequence)` 那条规则的 target_table，丢失了早期步骤写的表。

**修复**：`group_target` 改为 `dict[dir]→set(targets)`，收集规则组**所有**规则写过的 target_table；依赖匹配改为 `src_key in other_target_set`。

**验证**：
```
修复前：GRP_X seq=[0,1]，GRP_Y seq=[1]  → Y 没排在 X 后 ✗
修复后：GRP_X seq=[0,1]，GRP_Y seq=[3]  → Y 正确排在 X 后 ✓
```

### BUG 2：环检测标志失效

**现象**：A↔B 互相读取构成真实环，但 `cycle_detected` 永远返回 False，调用方永远拿不到环信号，环被静默吞掉。

**根因**：`trace_upstream_rule_groups` 用 `len(visited_dirs) < len(groups)` 判断环，但每个进入 `groups` 的 dir 必先进入 `visited_dirs`，该条件**恒为 False**。

**修复**：引入 `pending_dirs`（当前递归栈中的目录集合），进入时 add、返回时 discard；`cycle_detected` 改为「遇到已在 pending 中的 dir 即标记」，真实反映是否存在环。

**验证**：
```
修复前：A↔B 环 → cycle_detected=False ✗
修复后：A↔B 环 → cycle_detected=True ✓（且不死循环）
```

### BUG 3：max_depth 静默截断

**现象**：超过最大深度（默认 6）的上游规则组被静默丢弃，调用方无法区分"自然到顶 ODS"和"被深度截断"。

**根因**：`depth > max_depth` 时直接 return，无任何上报；返回值也没有截断标记字段。

**修复**：新增 `truncated`（bool）字段，当因 depth 超限提前返回时置 True；docstring 同步更新返回结构。

**验证**：
```
修复前：8 层链路只追溯出 7 层，not_found 为空，无任何截断信号 ✗
修复后：8 层链路追溯出 7 层，truncated=True ✓；7 层链路 truncated=False ✓
```
