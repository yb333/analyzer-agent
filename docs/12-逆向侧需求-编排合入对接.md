# 12 · 逆向侧需求：编排合入对接（v2，发 dws-analyzer-skill）

> 目标读者：analyzer 侧维护会话。背景：2026-10-14 消费侧契约演进讨论定稿（00 章修订记录 v3.0）。本文是 v2 对接需求清单——**只提我们需要的输出、调用方式、输入形态与开发协议；逆向侧内部怎么实现（解析语料/方言/AI 增强步骤/知识结构）不在范围**。
> 与既有交接的关系：09=接口契约（v1.1 已双方实施）；10=v1.0 导出能力实施需求（含 knowledge_draft 字段映射——内部实现细节，保留为历史交接基线，本文不替代其验收效力）；**本文=v2 增量需求**，经你们确认后按 §六 波次实施，schema 升版纪要回填 09。

## 一、调用方式（v2 变化：文件交接 → 编排合入）

- 消费侧新增薄 agent `dws-reverser`（岗位定义在 design-dev-agent 仓：身份=逆向翻译者+权限+指向你们的 skill，同 designer/coder 模式），优化流程步骤 0 无档分支 **Task 自动起调**。
- 输入传递：任务 prompt 携带 {制品文件路径清单, 资产标识 schema.table, 输出落盘路径}；产物 = 约定路径的 `baseline_v1.json`。
- **一次调用一次交卷**：多制品一次收全、一次产出，流程不做反复调用（你们内部跑几轮自检迭代是实现自由，流程只认交卷时契约是绿的）。
- **不变项**：我们仍不调你们的任何脚本（起调的是 agent，不是 run.py）；契约仍以文件形态落盘交接；真第三方供方出现时可退回"直交 json"旧模式（兼容保留）。
- **需你们确认**：skill 在内网的安装名/位置（dws-reverser 的 skill 指针按 opencode 安装名解析，不按仓路径）。

## 二、输出规格

### 2.1 交卷标准（契约级，四条纪律）

1. **逐字保真**（延续 v1.0）：query_sql / raw_expr / delete_condition 逐字节保留解析原文——不美化、不重排版、不规范化大小写。机械错（漏/错字符）双跑时会炸出来，理解性改写是 silent 错、绝对禁止。
2. **显式空**（延续 v1.0）：拿不到的信息 = 显式 null 或空数组，不省略 key——静默缺失让我们无法区分"没有"和"忘了"。
3. **自校验后落盘 → 交卷即终态**（延续并升格）：产物过仓内权威 schema 全绿才交卷；我们入料还会做确定性复核（schema + 内部一致性：SQL 引用表 ⊆ source_tables∪tables、lineage target ⊆ tables.fields），不通过 fail loud 退回。
4. **一次产全**（新增）：契约自足——后续流程（组装/围栏/双跑/制品 patch/回刷）需要的物理事实一次交齐，漏项只能显式 null+warnings，不能缺失。逆向对同一资产只发生一次，交卷后流程永不回头再问。

### 2.2 我们要的字段（消费端倒推——契约字段 = 消费点需求并集）

| 消费点 | 依赖字段 | 缺了会怎样 |
|--------|---------|-----------|
| ts_baseline 组装（designer 开工地基） | rules[]（query_sql/delete_mode/delete_condition/merge_on/source_tables/target）、tables[].fields | 组不出来，死在入料 |
| 围栏冻结层（变更恰好等于声明） | tables[].fields 集合、lineage[].raw_expr、query_sql——**全部逐字** | 锚点漂移，围栏误报/漏报 |
| 双跑（老列逐值一致） | query_sql（落盘为 baseline SQL） | 没有对比基准 |
| 增量/回刷 | delete_condition、schedule.params（增量变量）、merge_on | 回刷脚本无从生成 |
| 制品 patch | provenance（xlsx=文件+sheet 定位；DDL/代码仓=路径清单） | patch 底本取不到，问人 |
| designer 理解存量 | joins/where_clause/group_by、warnings、patterns(hint) | designer 只能硬啃 SQL 原文 |
| 完备性自证 | version、warnings[]（"拿不到的事实"显式化通道） | 缺失静默化 = 漏 |

### 2.3 相对 v1.1 的扩充需求（需双方确认后 schema 升版，见 §五议题 3）

| 字段 | 扩充内容 | 消费动机 |
|------|---------|---------|
| tables[].fields | 补物理属性：分布键/分区键（及 DDL 表级属性） | 档案 DDL 走 ts 投影再生——投影无损的前提是 ts.tables 完整承载 DDL 细节 |
| dq_rules[] | 补平台规则编码（rule_code 原值）+ 告警配置（接收人/级别） | DQ 制品通道统一为 dq.json 重建：存量规则沿用原编码是平台识别"同一条规则"的锚（编码不变才不重复建），重建需要告警配置 |
| provenance[] | 定位粒度按制品类型：xlsx=文件+sheet 定位；DDL/代码仓=路径清单 | patch 底本定位与 provenance 人肉回查 |

每项请回告**逆向可得性**——拿不到的字段走显式 null+warnings 通道，不算违约。

### 2.4 明确不要的（边界重申）

- **语义判断永不进契约**：增量字段、驱动表、主键、粒度——哪怕解析时能推测也不给（归人回路）。
- **不要求产出归一 DDL 文件**：原始 DDL 只是你们的事实来源（喂 tables 段），读完即弃——消费方档案的 DDL 由 ts 投影生成。
- **不要求产出 mapping**：业务侧交付物，与你们无关。
- spec 草稿（契约 B，给 RS 段）**不进我们的档案**，见 §五议题 2。

## 三、消费侧定义的用户输入（你们将拿到的燃料）

**首优一次**（存量资产首次优化；制品此时在手边最全）：

| 制品 | 形态 | 要求 |
|------|------|------|
| 术加制品包 | excel（平台格式） | **必给**——query_sql 唯一来源，无兜底通道 |
| LTS 制品 | excel（平台格式） | **增量资产必给**（增量变量还原=回刷地基）；全量资产可不给 |
| DQ 制品 | excel（平台格式） | **三态**：给文件 ｜ 用户声明"资产无 DQ"（声明入档，此后永不再问）｜ 沉默——我们拦下问，不猜 |
| DDL | SQL 文件（可多个，原始命名随意） | 给则用；缺则我方 precheck 连库回填（★若你们能从库导表结构，用户可彻底免提供——§五议题 1） |

**二优起**：用户不再提供任何制品（档案接管）。逆向对同一资产只发生一次（覆盖重入料除外）。

## 四、职责边界（谁做什么）

- **逆向**：解析制品 → 产 baseline_v1.json（一次交卷）。
- **我方**：契约校验 → 建档（ts_baseline 组装 / etl 逐字落盘 / **原始制品拷入档案 export/**[术加·LTS·DQ excel=patch 底本] / ddl/ 由 ts 投影）→ 此后档案接管、逆向退场。
- 两仓各自维护各自的 git 与内网同步链路，互不嵌套；联动只发生在契约变更波（§六）。

## 五、待讨论议题（下次对接过一遍）

1. **DDL 从库导出能力**：能做则用户免提供 DDL 文件（tables.fields 连库兜底通道前移到逆向侧）。
2. **一次调用同时产 baseline_v1 + spec 草稿（契约 B，给 RS 段）的可行性**：对原始制品只解析一遍，两个输出两个消费方、互不牵连。
3. **§2.3 三项扩充字段的逆向可得性**与 schema 升版节奏（v1.2）。
4. **DQ excel 平台侧字段盘点**：告警配置之外还有什么平台独有信息——DQ 重建"投影无损"前提的验证。
5. **analyzer 内网部署形态**：skill 安装名/位置，dws-reverser 指针兼容性。

## 六、开发协议（契约演进波次）

- **变更波次固定**：① analyzer 仓先行（schema+契约文档+fixtures+version bump——生产方权威，我们永不先改 vendor）→ ② 我方跟随（re-vendor + 消费端适配 + 契约测试绿）→ ③ 同一波内两仓各自同步内网。无契约变更的日常提交两仓完全独立、零协调。
- **联锁（我方实施挂起）**：我方同步工具将加联锁检查——vendor 版本 vs 你们仓 schema 版本不一致即拦截（把契约漂移的发现点从内网运行时 fail-loud 提前到本地同步时）。
- **双端契约测试维持现状**：fixture 不跨仓 import，双方 CI 各自跑。
