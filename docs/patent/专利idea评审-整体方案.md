# 专利 idea 评审材料：数据资产确定性认知底座（数据资产 init）——主创新点与子专利点拆解

> 状态：内部 idea 评审稿（伞柱结构版）。标注【待补】处需填实测数据或内部信息。
> 结构说明：**主创新点（伞）= 项目核心能力**：数据资产 init——多源制品确定性翻译为可信认知地基，多场景 AI 消费。因上位概念已有近邻占位、完整闭环不宜单件包揽，拆解为**三个子专利点（柱）**落地申请：① 变更影响判定 ② 制品指纹分拣与错配拦截 ③ AI 逆向产物的审核晋级与建档。

---

## 一、idea 产生的背景与现有技术

### 1.1 背景：数据交付全流程 AI 化卡在"存量资产认知断层"

数据交付全流程（DDLC：需求 → 设计开发 → 测试 → 部署 → 运维）正在 AI 化：设计开发段已有 agent 连续完成粗设计 → 细设计 → 编码 → UT（内部已运行）。但**存量资产是这条流水线的隐形断层**——AI 面对一个存量 ETL 资产时没有可读的东西：加工逻辑锁在平台导出制品（xlsx/yml）与 SQL 中，调度配置在 LTS、质量规则在 DQ、表结构在 DDL，散落五处、格式各异。每个针对存量资产的 AI 任务，都得先人工"喂现状"。

**init 类比**：代码项目 init 后 AI 开箱即用（源码、README、结构约定即机器可读认知材料）；数据资产的等价物不存在。本项目即**数据资产的 init**：把多源制品确定性翻译成机器可读、证据可溯、零伪造的资产认知地基（asset_facts 事实包），并以审核建档机制使其成为可信基线（git 对象），AI 在其上开展深度工作。**已运行的消费场景**：变更影响分析（单资产全流程已实现）、优化设计初始化（向设计开发 agent 供给存量基线，已对接运行）、资产文档化、字段检索。

要使这个 init 成立，须解决三个子问题：

- **原料问题**：多类平台制品（执行规则/调度/质量，物理上全是 xlsx）装配靠人工指认，指认错误静默污染下游全部分析
- **信任问题**：机器逆向产物凭什么可信？错误的事实包一旦被当作开发基线，污染下游整个 AI 开发生命周期（增量设计、编码、UT 全部建立在错误现状上）
- **消费问题**：认知地基如何让多个 AI 场景复用（影响分析/优化设计/文档化），而非一个场景一份解析

### 1.2 现有技术及其缺陷

| 现有技术 | 做法 | 缺陷（对应三子问题） |
|---------|------|---------------------|
| 血缘平台影响分析（内部血缘平台、DataWorks/DataArts 类） | 依赖图遍历列举下游 | 只解决"找"不解决"判"——遍历命中即报影响，假阳性爆炸（消费问题的另一面） |
| 开源字段血缘工具（SQLLineage 等） | SQL → 字段映射 | 只做血缘生成，无消费场景深度 |
| DataHub Agent Context Kit / AWS Context Intelligence / DataWorks Data Agent | 元数据派生的 agent 上下文（表结构/血缘/标签） | **原料浅**（元数据派生，无表达式级加工事实）、**无供给纪律**（无防伪造/防缺失误读设计）、**无信任治理**（即用即弃查询上下文，无"审核→可信基线→演进"机制） |
| CI 供应链验证（签名/provenance）、medallion 分层 | 产物签名验证 / 数据值分级晋级 | 验签名不验内容一致性；晋级的是数据值非规格事实（信任问题的近邻但不覆盖） |
| 文件格式嗅探、ETL 平台连接器 | magic number / 人工配置源类型 | 只认物理格式，xlsx 间业务结构差异不可见；错配无装配层拦截（原料问题无解） |

## 二、本 idea 的技术方案（认知底座 + 治理闭环）

### 2.1 总览：逆向 → 建档 → 消费 → 演进

```
┌─────────────── 认知底座（analyzer）─────────────────┐
│ ① 逆向：多源制品装配（指纹分拣+四道拦截）             │
│    → 确定性解析引擎 → asset_facts 事实包（守恒契约）  │
├─────────────────────────────────────────────────────┤
│ ② 建档：入料审核（五类对账）→ 资产档案（git 对象）    │
│    暂存区 reverse/（自由重跑）──审核──▶ 确认区 archive/│
├─────────────────────────────────────────────────────┤
│ ③ 消费：场景投影（引擎无场景感知，加场景零引擎改动）   │
└─────────────────────────────────────────────────────┘
     ↓ 消费场景（已运行）              ↓ 演进
   影响分析（判定链+三态输出）        交付收口 → 档案推进
   优化设计初始化（ts_baseline）      （advance 动作）
   文档化 / 字段检索 / ……
```

### 2.2 逆向段：多源制品 → 确定性事实包

**制品装配**（解决原料问题）：对三类平台制品定义必选 sheet 结构指纹（执行规则包=RULE+TargetFields；调度包=tasks/jobs/taskParams；质量包=规则基础信息主 sheet，实测指纹不重叠），目录通道自动判型路由；四道错配拦截——格式（指纹不符 fail loud 指明缺什么）、多义（同型多文件不静默取一）、声明（指认优先仲裁+声明/发现矛盾检测）、串包（末端制品目标表 vs 声明资产强校验）。

**确定性解析引擎**（纯函数、方言适配）：CTE 单层/嵌套/递归穿透到物理源表、JOIN 键血缘、UNION/窗口函数/行转列、注释别名识别。产出字段级映射，**携带每跳表达式原文**。全程确定性文法解析（sqlglot AST），非概率推断。

**信息守恒契约**（事实包质量规范）：逐字保真（SQL/条件原文逐字节保留作证据锚点）、显式空（拿不到=显式 null，区分"没有"与"忘了"）、无假信息（解析不出=null+warning 披露，绝不伪造；确定性文法解析与业务语义推断严格分界）。事实包自带**交付自检**：三态结论（pass / pass_with_noise / review）+ 严重度分级（结构级/噪音级）+ 一致性交叉检查。

### 2.3 建档段：审核晋级 → 可信基线（解决信任问题）

逆向产物落暂存区（自由区，可删可重跑，不参与路由判断）；经**入料审核**（确定性门，五类对账）才能建档——档案为 git 合入对象、资产唯一权威形态（ts.json + DDL + SQL + DQ + 制品 + MANIFEST 版本索引）。

**五类对账**：① 契约一致性（版本/schema/内部一致性校验）② 跨系统资产身份对账（产物资产标识 vs 任务参数，镜像归一后比对，不一致=串包拒收）③ **变更时序对账**（变更台账最新批次的新增字段若已存在于产物字段集 → 制品新鲜度冲突——变更疑似已执行，检测两个系统的时间线一致性）④ 反向台账对账（产物有、台账当前态无、也非本批新增 → 台账滞后，warn 披露）⑤ 上游自检结论分级消费（review=结构级矛盾拦截待人审，人审显式放行且裁决留痕；pass/pass_with_noise=噪音计数披露；旧版本产物无自检字段=降级折叠披露）。

**拦截-处置路由绑定**：每类拦截自带确定性处置路由（契约问题退逆向侧原样退回 / 串包换料 / 新鲜度冲突三选一人决策 / 格式问题按规范改输入），**AI 在门内零裁量**——不代填、不重试绕过、上报即止。审核不过档案不诞生（失败零残留）。

**建档组装**（ts_baseline，技术规格形状的存量基线）：文法/拓扑可推导的结构事实填充（表角色/交叉读写/依赖拓扑）；设计判断语义位显式留空+豁免清单（business_key/grain/join_safety 等，绝不伪造）；写入类型词表映射覆盖不了的留空记"待定"（无假信息纪律的消费端镜像）。

### 2.4 消费段：多场景 AI 基于档案工作

**场景无关架构**：引擎/装配层不知道消费场景（接口只描述"要什么"，无 `if 场景` 分支）；场景差异全部留在投影层（只裁剪不重算，单一权威生产点）——从文档化到影响到优化初始化，引擎零改动。

**消费场景一：变更影响分析**（最深的场景，此处为证据）。输入变更清单（只描述"什么变了"）+ 字段级映射 + 目标 DDL：三层过滤（表级/字段级/命中）→ 确定性传播（跳内边=表达式列依赖、跳间边=别名对齐，计算波及域，不判影响）→ **语义影响判定**（类型家族归一化 + 长度/精度/标度提取 + cast 关口吸收判定 + 扩缩容方向判定 + 变化类型映射，变更类型×沿途表达式×目标 DDL 三方交叉）→ 三态输出（🔴有影响/🟡待确认/🟢无影响，附传播路径、每跳表达式、判定原因、"去哪看"定位）；SELECT \* 等不可枚举字段场景显式标待确认+步骤定位，不猜。三态进一步驱动跨资产逐层分析路由（🔴🟡传播/🟢⚪截断/深度上限防环，与血缘平台交替确认，逐层收敛）。

**消费场景二：优化设计初始化**（已对接设计开发 agent）。ts_baseline 为地基：AI 基于"结构事实已填充+语义位显式留空+豁免清单"的基线做增量设计（新增字段第一刀已运行），全程围栏（设计边界检查/SQL 围栏）与闸口（人审确认点）护栏；交付收口后档案推进（advance），档案随每次变更持续演进。

**消费场景三**：资产文档化（字段映射/资产说明书/技术设计三件套）、字段检索、DQ 质量画像（作为资产画像组成，不独立成场景）。

**消费场景四（设计中，原理闭合）：变更驱动的优化闭环**——影响分析 × 优化初始化的串联：源端变更通知 → 影响清单（🔴🟡 + 传播路径 + 去哪看定位）【已运行】→ AI 解读层逐条解读（自包含清单原则：每条原子事实自带全部证据——变更、路径、每跳表达式、目标 DDL、判定状态——AI 逐行理解不碰全图，结论点回原子事实可追溯）【确定性设计】→ 基于档案基线（ts_baseline + SQL 原文）生成变更方案草稿 → 进入增量设计流程（围栏/闸口/UT 护栏）【已运行】→ 人审后执行、档案推进。全链无概率性环节兜底假设。

### 2.5 演进：档案生长与规模化

- **档案演进**（已实现）：adopt 首优收档 / advance 交付收口推进——档案为 git 对象，资产随每次变更可追溯演进。
- **AI 解读层**（设计中，确定性设计）：确定性清单 → AI 逐条解读 → 报告；"每句 AI 结论都能点回清单某条原子事实"的可追溯铁律 + 显式置信度已写入设计；确定性层替 AI 干掉图遍历（最易幻觉的部分），AI 只理解单行表达式级事实。
- **资产认知库规模化**（演进方向）：批量逆向全代码仓 → 全量资产的 facts 集合与统一资产目录——**单资产深度事实的规模化聚合**（跨资产图遍历仍与血缘平台协作，不自建图谱）。

## 三、与业界方案的对比（业界为什么没做到）

**根本原因一：知识粒度缺口径（影响判定做不到）。** 血缘平台依赖图只有"边"没有"边上的语义"（有无 cast、什么表达式）——影响实质判定所需的每跳表达式与目标 DDL 类型在依赖图这个数据结构里不存在，业界产品只能停在"列举"。本方案从制品 SQL 原文出发解析出每跳表达式，判定层有了原料。

**根本原因二：通用性包袱（类型深判不敢做）。** 商业产品面向多库多方言，类型系统兼容语义无法统一深判；本方案面向单一数仓平台类型系统，可做家族归一+精度标度+方向判定。

**根本原因三：开放集合 vs 封闭集合（制品分拣没人做）。** 通用平台接入源是开放集合，结构无法枚举只能人工配置；本方案面向封闭的平台制品集合（三类固定结构），指纹可定义可枚举，自动分型+分层拦截才可行。

**根本原因四：上下文供给与信任治理割裂（业界只供上下文，不管产物可信）。** DataHub/AWS 型 agent 上下文是即用即弃的查询供给——没有"机器产物凭什么可信"的机制：无内容级对账（CI 供应链验签名不验内容）、无审核晋级（medallion 晋级数据值不晋级规格事实）、无基线演进治理。本方案将"逆向产物→确定性对账→可信基线→持续演进"做成闭环，错误产物在入档前被拦截（零残留）。

### 效果（2026-10-19 实测，详见《效果实证记录》，产物留档 docs/patent/实证产物/）

| 指标 | 基线（人工/遍历型/无此环节） | 本方案（实测） |
|------|---------------------------|---------------|
| 存量资产现状梳理（分拣+解析+自检全流程） | 人工【待补：人日】 | **0.4 秒** |
| 影响误报（同批 5 条命中变更） | 遍历型全报"受影响"=5 条待人工排查 | 🟢 吸收 1 条 + 🟡4 带原因与定位（🔴 方向另有实证：跨族 cast 关口判 high 带原因） |
| cast 关口双行为 | 结构上不可能（无表达式知识） | **实证**：同一扩容变更，DECIMAL 关口判 🔴 拦截 / varchar(50) 关口判 🟢 吸收，均带完整原因链 |
| 装配分拣 | 人工指认 | 混合目录（3 类制品+DDL+2 干扰文件）**7/7 分型正确，干扰显式披露 2/2** |
| 入料审核（串包/自检待审/契约违规坏料） | 无此环节 | **4/4 全拦截**，处置路由齐全，人审放行留痕，失败零残留 |

## 四、本 idea 的技术创新点（伞 + 三柱）

> 呈现结构：主创新点（伞）是核心能力；子专利点（柱）是落地拆解。伞做叙事与体系，柱做权利要求。

### 主创新点（伞）：场景无关的数据资产确定性认知底座（数据资产 init）

**主张**：多源非代码制品 → 确定性解析 → 守恒契约事实包 → 审核建档为可信基线（git 对象）→ 多场景 AI 消费与持续演进。三个机制支柱：**场景无关架构**（引擎无场景感知，场景差异全留投影层——从文档化到影响到优化，引擎零改动）、**信息守恒三律**（逐字保真/显式空/无假信息——防 AI 将缺失解读为否定、防源头污染、证据可锚定）、**两态信任治理**（暂存区自由重跑，档案审核才诞生，失败零残留）。
**与业界区别**：DataHub/AWS 型上下文为元数据浅层派生、即用即弃、无供给纪律、无建档治理；本方案为制品原文、表达式级深度、守恒契约、档案化演进闭环（原料/深度/纪律/治理四层差异）。
**不单独成件的原因**：上位概念（给 agent 供数据资产上下文）已被产品公开占位，单独申请需深层特征堆叠与近邻缠斗；完整闭环含六段（分拣/解析/契约/审核/建档/消费），单件包揽则任一段被对比文件击中整体即倒。故拆三柱落地，柱的组合覆盖伞的各关键截面。

### 子专利点 1（柱 1）：变更影响判定——传播与判定分离 + 类型兼容性链

**主张**：确定性传播（波及域计算，跳内表达式列依赖+跳间别名对齐）与语义影响判定解耦为两独立阶段；判定层为变更类型×沿途表达式×目标 DDL 三方交叉的判定链（类型家族归一化+精度标度提取+cast 关口吸收+扩缩容方向判定+变化类型映射）；三态输出，三态再驱动跨资产逐层截断路由（确定无影响截断/待确认保守传播/深度上限防环）。
**区别**：遍历型方案无判定阶段（依赖图知识结构里判定层无处安放）；编译器类型检查不携带变更传播语义，血缘传播不携带类型语义——两类现有技术的交叉地带无人做过。
**典型例**：varchar(20)→(50) 扩容经 cast(col as bigint)——遍历型报"有影响"，本方案判"被关口吸收，无影响"。
**延伸实施例（设计中，原理闭合）**：三态输出的消费闭环——影响清单 → AI 逐条解读（自包含原子事实）→ 基于档案基线生成变更方案草稿 → 增量设计流程人审执行、档案推进。

### 子专利点 2（柱 2）：制品结构指纹分拣与四道错配拦截

**主张**：同物理格式（xlsx）、不同业务结构的平台制品按 sheet 结构指纹自动判型并路由解析通道；格式/多义/声明/串包四类错配在装配层显式拦截（fail loud 不猜、不静默消歧；显式指认与自动发现的优先级仲裁+声明/发现矛盾检测；末端资产强校验兜底）。
**区别**：格式嗅探只认物理层（ZIP 容器内业务结构不可见）；元数据/ETL 平台连接器靠人工配置，错配在深层解析才暴露，装配层无防御。

### 子专利点 3（柱 3）：AI 逆向产物的确定性审核晋级与基线建档

**主张**：机器逆向产物在成为 AI 开发基线前过确定性对账门——五类对账（契约一致性/跨系统资产身份/变更时序/反向台账/上游自检三态分级消费）；拦截自带确定性处置路由，**AI 在门内零裁量**（不代填、不重试绕过、上报即止），人审裁决显式留痕；审核不过档案不诞生（零残留），过了组装 ts_baseline 建档（结构事实填充+语义位留空+豁免清单，绝不伪造）为 git 对象，交付收口后档案推进演进。
**区别**：CI 供应链验证验签名不验内容一致性；medallion 分层晋级数据值非规格事实；ETL 对账对的是数据值，非"逆向规格事实×变更台账×任务参数"的交叉对账。其中**变更时序对账**（制品字段集与变更台账批次的时间线一致性检测）与 **AI 门内零裁量的处置路由**（AI 生成产物信任边界的确定性机制）在近邻中无教唆。
**场景语境**：AI 生成产物的可信性是当前工程焦点——"AI 逆向产物经确定性门晋级为 AI 开发基线"具有时代性技术问题（错误基线污染下游 AI 开发生命周期）。

### 观察项：认知包本体（信息守恒三律）

暂不单独主张（agent 上下文域专利态势未清）；三律已作为伞的机制支柱与柱 3 的上游（自检三态）分布落地。
