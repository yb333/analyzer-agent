# 专利 idea 评审材料大纲（伞柱结构版）

> 结构定调（2026-10 与作者对齐）：**主创新点 = 项目核心能力（数据资产 init / 确定性认知底座），子专利点 = 核心能力的落地拆解（三柱）**。评委看到的是战略级构想 + 可落地的专利路径。
> 讲述时长基准：15 分钟陈述 + 问答；PPT 12~15 页；材料全文作 handout。

---

## 开篇：30 秒定位句（第一页）

> **"代码项目有 init——init 完 AI 就能干活；数据资产没有 init——存量资产的加工逻辑锁在平台制品里，AI 无从认知，数据交付全流程的 AI 化因此卡在中游。我们做的就是这个 init：把多源制品确定性翻译成可信的资产认知地基，AI 在地基上做影响分析、做优化设计——这两个场景已经在跑。"**

作用：一句话立住"基础设施"定位 + 给出两个已运行场景的实证钩子，评委带着"地基长什么样、怎么可信、AI 怎么用"三个问题往下听。

## 一、背景叙事（init 主线，3~4 页）

### 讲什么

**1. 从行业级痛点切入（格局要大，不是单点工具的痛）**
数据交付全流程（DDLC：需求 → 设计开发 → 测试 → 部署 → 运维）正在 AI 化：设计开发段已有 agent 连续完成粗设计→细设计→编码→UT（内部已有项目在跑）。但存量资产是这个流程的隐形断层——**AI 面对一个存量 ETL 资产时，没有可读的东西**：加工逻辑锁在平台导出制品（xlsx/yml）和 SQL 里，调度在 LTS、质量规则在 DQ、表结构在 DDL，散落五处、格式各异。每个要做存量优化的 agent 任务，都得先人工"喂现状"。

**2. 类比定调（init 类比的完整展开）**
代码项目 init 后 AI 开箱即用——源码、README、结构约定本身就是机器可读认知材料。数据资产的等价物不存在。业界近两年出现 agent 上下文供给方向（DataHub Agent Context Kit / AWS Context Intelligence / DataWorks Data Agent），但它们的上下文是**元数据中心派生的浅层信息**（表结构、表级血缘、业务标签）——不含加工逻辑深层的确定性事实，撑不起优化设计、影响判定这类深度任务。

**3. 三个子问题（init 要解决什么）**
- **原料问题**：多源制品装配靠人工指认，错配静默污染下游
- **信任问题**：机器逆向产物凭什么可信？错误的事实包一旦当基线，污染整个下游开发生命周期
- **消费问题**：认知地基怎么让多个 AI 场景复用（影响分析/优化设计/文档化），而不是一个场景一份解析

**4. init 的实际形态（升维后的落点，一段）**
本项目的产出不是一个工具，是**资产认知底座 + 治理闭环**：逆向（多源制品→确定性事实包）→ 建档（入料审核→资产档案=git 对象=可信基线）→ 消费（多场景 AI 基于档案干活）→ 演进（交付收口后档案推进）。影响分析、优化设计初始化是已运行的消费场景。

**5. 现有技术缺陷表（一张表收束）**
| 现有技术 | 做到 | 缺 |
|---------|------|----|
| 血缘平台影响分析（遍历列举型） | 找下游 | 不判实质，假阳性 |
| DataHub/AWS 型 agent 上下文 | 浅层元数据上下文 | 元数据派生，无表达式深度，无供给纪律，无建档治理 |
| 开源血缘工具 | 生成血缘 | 不做判定、不做消费 |
| CI 供应链验证 / medallion 分层 | 产物签名验证 / 数据值分层晋级 | 验签名不验内容一致性；对账数据值不对账规格事实 |

**6. 业界为什么做不到（四个根本原因，叙事收束）**
① 知识粒度缺口径（依赖图无表达式语义）② 通用性包袱（多方言不敢做类型深判）③ 开放集合 vs 封闭集合（制品指纹可枚举才可自动分拣）④ 上下文供给与信任治理割裂（业界只供上下文，无"逆向产物→审核→可信基线"的晋级机制）。

### 写法纪律
- 每句"业界没有/做不到"必须经检索验证
- 痛点讲 DDLC 断层，不讲"我们工具缺什么功能"——评委听的是行业问题不是产品问题
- 叙事逻辑链：DDLC AI 化的断层 → init 缺失 → init 长什么样 → 三个子问题 → 我们的底座与闭环

## 二、技术方案（大循环 + 底座架构，4~5 页）

### 讲什么

**1. 一张总览图**（评委记住图 = 记住方案）：

```
┌─────────────── 认知底座（本仓：analyzer）───────────────┐
│ ① 逆向：多源制品装配（指纹分拣+四道拦截）                 │
│    → 确定性解析引擎 → asset_facts 事实包（守恒契约）      │
├──────────────────────────────────────────────────────────┤
│ ② 建档：入料审核（五类对账）→ 资产档案（git 对象=可信基线）│
│    （暂存区 reverse/ 自由可重跑 ──审核──▶ 确认区 archive/）│
├──────────────────────────────────────────────────────────┤
│ ③ 消费：场景投影（引擎无场景感知，场景差异全在投影层）     │
└──────────────────────────────────────────────────────────┘
        ↓ 消费场景（已运行）
   影响分析：三层过滤→确定性传播→语义判定→三态输出
   优化设计初始化：ts_baseline 组装（结构事实填充+语义位留空+豁免清单）
   文档化 / 字段检索 / ……
        ↓
   ④ 演进：交付收口 → 档案推进（advance）
```

**2. 三段讲法**：
- **底座段**（逆向+建档）：制品指纹分拣、确定性解析（CTE 穿透/JOIN 键追溯/每跳表达式原文）、信息守恒三律；入料审核五类对账、两态治理、ts_baseline 组装原则（可推导的填/语义位留空/不伪造）
- **消费段**：以影响分析为主例展开（三层过滤→两类边传播→判定链五要素→三态输出），优化初始化为次例（design-dev-agent 拿档案做增量设计，围栏/闸口护栏）——**影响分析在这里是"证据"不是"主角"**
- **演进段**：adopt/advance 两动作，档案随交付持续演进

**3. 详略分配**：底座段 40%、消费段（影响分析为主）40%、演进段 20%。术语全文统一：认知包/事实包、波及域、判定链、关口吸收、三态输出、四道拦截、五类对账、两态治理、可信基线。

### 写法纪律
- 不贴代码/schema，讲机制不讲实现
- 每段存在理由回扣背景三问题（原料→分拣；信任→对账建档；消费→场景无关架构）
- 关键机制标注"→ 见子专利点 N"，方案与专利点互相锚定

## 四、创新点（伞 + 三柱，核心页 2~3 页）

### 提炼标准（元方法，答辩时回应"点太散"的总框架）
四要素齐全才算成点：**可命名标题 / 一句话主张（做什么+区别于什么）/ 位置感 / 预置反问应对**。

### 未实现内容的写法纪律（"可吹"的边界）

idea 评审允许包含未实现内容（能说清原理、方案闭合即可），但须守三条纪律：

1. **三档分级显式标注**：已运行 / 已对接 / 设计中（原理闭合）。分级本身是可信度资产——评委看到的是有规划的体系在生长，不是画饼；被追问时有准确退守位置。
2. **位置规则**：背景展望、方案演进段、创新点延伸实施例、保护点从属特征——可吹；**实现效果表绝不吹**（效果数字必须真实，评委必查，一处露馅全盘陪葬）。
3. **原理闭合检查**：每个"设计中"内容答辩前过一遍——每一步能说清由哪个已运行组件或确定性设计支撑，被追问"怎么实现"时能当场画机制图；无机制说明的纯愿景不写。

当前材料"设计中"内容清单（均已过原理闭合检查）：变更驱动优化闭环（影响清单→AI 解读→方案草稿→增量设计，柱 1 延伸实施例）、AI 解读层（自包含清单原则）、资产库规模化（单资产事实聚合，与血缘平台划界）、跨资产逐层交替（柱 1 组成，设计定稿）。

### 呈现结构
一伞 + 三柱 + 一观察项。伞是核心能力（idea 的主体），柱是落地拆解（专利申请的单位）。伞详写四要素；柱各写四要素但主张聚焦权利要求核心。

---

**主创新点（伞）：场景无关的数据资产确定性认知底座（数据资产 init）**

- **主张**：多源非代码制品 → 确定性解析 → 守恒契约事实包 → 审核建档为可信基线（git 对象）→ 多场景 AI 消费与持续演进。三个机制支柱：引擎无场景感知（场景差异全留投影层，加场景零引擎改动）、信息守恒三律（逐字保真/显式空/无假信息）、两态信任治理（暂存区自由重跑，档案审核才诞生）。
- **位置**：整个方案（①②③④ 大循环）。
- **与业界区别**：DataHub/AWS 为元数据浅层派生、即用即弃查询上下文、无供给纪律、无建档治理——本方案为制品原文、表达式级深度、守恒契约、档案化演进闭环。
- **反问应对**（"这不就是给 agent 供上下文吗"）：供上下文只是消费段的表象；差异在原料（制品原文 vs 元数据）、深度（表达式级 vs 表级）、纪律（守恒契约 vs 无）、治理（建档晋级 vs 即用即弃）四层。
- **为什么伞不单独成件**（评委必问，标准答案）：上位概念被 DataHub/AWS 产品公开占位，单独申请需深层特征堆叠缠斗；闭环六段塞一件则任何一段被击中整体倒。拆三柱落地，柱的组合覆盖伞的各关键截面——**伞做叙事与体系，柱做权利要求**。

**子专利点 1（柱 1）：变更影响判定——传播与判定分离 + 类型兼容性链**（消费段·场景层）
- **主张**：确定性传播（波及域计算）与语义影响判定解耦两阶段；判定层 = 类型家族归一化 + 精度标度提取 + cast 关口吸收 + 扩缩容方向判定 + 变化类型映射，构成变更×表达式×目标 DDL 三方交叉判定链；三态输出（有影响/待确认/无影响），三态再驱动跨资产逐层截断路由。
- **区别**：遍历型方案无判定阶段（依赖图知识结构里判定层无处安放）；编译器类型检查不携带变更传播语义。
- **反问应对**（"类型检查常规"/"图剪枝公知"）：单点常规，嵌入传播路径每条边逐跳判定+三方交叉是新的；剪枝信号来自判定层语义状态，非图结构属性。
- **弹药**：varchar(20)→(50) 经 cast(col as bigint)——遍历型报有影响，本方案判被吸收无影响。

**子专利点 2（柱 2）：制品结构指纹分拣与四道错配拦截**（底座·入口）
- **主张**：同物理格式、不同业务结构的平台制品按 sheet 结构指纹自动判型路由；格式/多义/声明/串包四类错配在装配层显式拦截（fail loud 不猜、声明与发现矛盾检测、末端资产强校验兜底）。
- **区别**：格式嗅探只认物理层；平台连接器靠人工配置，错配在深层解析才暴露。
- **反问应对**（"文件识别常规"）：识别只是入口，四道拦截是装配期断言体系——业界无"业务制品分型+错配分层拦截"方案。

**子专利点 3（柱 3）：AI 逆向产物的确定性审核晋级与基线建档**（底座·信任门）
- **主张**：机器逆向产物在成为 AI 开发基线前过确定性对账门——五类对账：① 契约一致性（版本/schema/内部一致）② 跨系统资产身份对账（归一化比对，不一致=串包拒收）③ **变更时序对账**（变更台账最新批次新增字段 ∈ 产物字段集 → 制品新鲜度冲突检测）④ 反向台账对账（产物有台账无 → 滞后披露）⑤ 上游自检结论分级消费（三态：待审拦截+人审显式放行留痕 / 通过 / 旧版本降级折叠）；拦截自带确定性处置路由（换料/退逆向侧/三选一人决策），AI 在门内零裁量（不代填、不重试绕过、上报即止）；审核不过档案不诞生（零残留），过了组装 ts_baseline（结构事实填充+语义位留空+豁免清单，不伪造）入档为 git 对象。
- **区别**：CI 供应链验证验签名不验内容一致性；medallion 分层晋级的是数据值非规格事实；ETL 对账对数据值非"逆向事实×多源台账"的交叉对账。
- **反问应对**（"数据校验+工作流常规"）：对账对象是"逆向生成的规格事实包与多源系统的多维一致性"，其中变更时序对账（两系统时间线一致性）与 AI 门内零裁量（人机信任边界的确定性机制）在近邻中无教唆。
- **场景红利**：AI 生成产物可信性是当前审查环境友好主题——"AI 逆向产物经确定性门晋级为 AI 开发基线"有时代语境。

**观察项：认知包本体（守恒契约三律）**
暂不单独主张（DataHub/AWS 域专利态势未清）；三律已作为伞的机制支柱与柱 3 的上游（自检三态）分布落地。

## 五、保护点（1~2 页）

**专利组合 = 伞做叙事，三柱做申请**：

| 件 | 子专利点 | 权利要求核心 | 授权把握 |
|----|---------|-------------|---------|
| 第一件 | 柱 1 | 获取字段级映射（血缘降格为输入）→ 传播 → 语义判定链 → 三态输出。必杀：cast 关口吸收、类型家族归一化、扩缩容方向、状态驱动截断 | 最高（公开池无判定层教唆） |
| 第二件 | 柱 2 | 指纹判型 → 路由 → 指认仲裁 → 矛盾检测 → 资产强校验，特征链窄写 | 较高（撞车风险最低） |
| 第三件 | 柱 3 | 五类对账 + 处置路由绑定 + 两态零残留 + 建档组装（留空+豁免）。必杀：变更时序对账、自检三态分级消费、AI 零裁量路由 | 中上（场景新，特征具体） |

**撰写策略**：柱 1 不以"解析 SQL/构建血缘"写起，全部步骤落在判定链——避开血缘红海与内部专利池；柱 3 背景落在"AI 生成产物可信性"时代问题，权利要求落在对账机制。三件背景技术均可引用内部血缘/影响分析专利论证空缺，形成引用网络。
