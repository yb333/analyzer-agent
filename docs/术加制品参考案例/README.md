## 一、Sheet 结构（名称必须逐字一致）

| Sheet | 作用 | 说明 |
|---|---|---|
| `RULE` | 规则主表 | 一个制品包 = 一个规则组，多行规则 |
| `GroupVariables` | 组变量 | 按规则编码挂参数（调度周期等） |
| `TargetFields` | 目标字段登记 | 按规则编码挂字段声明（类型/备注/别名） |
| `ModelRelations` / `ExtraFields` / `SPParams` / `Conditions` / `MaintenanceParams` / `Extract` / `ExtractColumn` | 其余标准页 | 通常为空表头行，**结构要保留**（真实导出固定结构） |

## 二、RULE sheet 关键列（解析器实际消费的 15 列）

其余 70+ 列可留空（真实导出大多为空）。**列名必须逐字匹配**。头号陷阱是查询语句列：
`(生成的）查询语句1`——**左括号是半角 `(`（U+0028），右括号是全角 `）`（U+FF09）**，
混排形态，手写必错；生成时直接从本案例 xlsx 复制表头行，不要手敲。

| 列 | 语义 | 取值示例 |
|---|---|---|
| 规则编码 | 规则唯一标识 | `R0001` |
| 规则中文名称 | 步骤业务名 | `资产明细加工` |
| 规则类型 | 见 §三枚举 | `1`（文本） |
| 执行序列 | 步骤顺序，**决定加工拓扑** | `1`/`2`/`3`（同序列不同分区=多场景并行） |
| 目标Schema / 目标表 | 本步骤写入的表 | `dws` / `tmp_cust_asset_detail` |
| 删除模式 / 删除条件 | 写入策略，见 §四 | `5` / `P_CUR` |
| (生成的）查询语句1~9 | SQL 原文，超长分列拼接（见 §五） | |

## 三、规则类型枚举（生成时按需选用）

| 类型 | 语义 | SQL 要求 |
|---|---|---|
| 1 / 14 | 取数 / Spark取数 | **必须有 SQL**，缺 SQL 的行会被静默丢弃 |
| 2 | 删数 | SQL 可选（记录操作） |
| 9 | 分区交换 | SQL 可选；**目标表=临时表，交换分区来源表=正式表** |
| 12 | 参数变量 | 不构成步骤（变量名填在「规则中文名称」列） |
| 10 / 11 / 13 / 15 | SP / API / 维护 / 判断 | 跳过，不进分析 |
| 其余 | 记录但不深度解析 | — |

## 四、删除模式枚举与「删除条件」语义（随模式变化，最易错）

| 模式 | 语义 | 删除条件列填什么 |
|---|---|---|
| 1 | TRUNCATE TABLE 全量清写 | 空 |
| 2 | 追加 | 空 |
| 3 | TRUNCATE SUBPARTITION | 子分区名/表达式 |
| 4 | DELETE | WHERE 谓词 |
| 5 | TRUNCATE PARTITION | **分区名**（同时是多场景分组依据，见 §六） |
| 6 | MERGE INTO 增量合并 | **MERGE ON 谓词**（如 `m.order_id = t.order_id`） |
| 7 | RPT_ITEM | 平台特殊语义 |
| 8 | UPDATE | WHERE 谓词 |
| 9 | 分区交换（与规则类型=9 配合） | — |

## 五、查询语句多列拼接规则

超长 SQL 分散在「查询语句1」「查询语句2」…列：按列号顺序**原样拼接非空列**
（不做 strip/美化，逐字保真是下游契约的地基）。本案例 R0002 故意拆成两列演示：
语句1 以别名 `t` 结尾、语句2 以 ` GROUP BY ...` 开头，拼接后语法完整。
**断句点必须保证拼接后 SQL 连续**（在列边界留空格或换行）。

## 六、多场景机制（执行序列 + 分区删除条件）

同一执行序列 + 删除模式 3/5 + 不同删除条件（分区名）→ 多场景并行写入同一目标表。
本案例：R0003（P_CUR 当日）与 R0004（P_HIS 历史）同为序列 3 → 解析为两个场景 +
公共步骤（R0001/R0002）。单场景资产不用刻意构造，一个分区或不填即默认场景。

## 八、常见错误清单（正向生成时逐条自检）

1. **列名不逐字匹配**：查询语句列的全角字符、`目标Schema` 的大小写——列名错=整列丢失；
2. **Sheet 名拼错**：必须是 `RULE` / `TargetFields` / `GroupVariables`（区分大小写）；
3. **类型 1/14 无 SQL**：该规则被静默丢弃（制品不完整且无提示）；
4. **TargetFields.规则编码与 RULE 行对不上**：字段声明悬挂，交叉验证全量报差异；
5. **删除条件填错语义**：dm=5 填了谓词、dm=6 填了分区名——下游写入计划直接错；
6. **类型 9 的目标表/交换表填反**：目标表列=临时表、交换分区来源表列=正式表；
7. **执行序列错乱**：拓扑顺序由执行序列决定，中间表步骤序列必须先于消费步骤；
8. **SQL 被美化/重排版**：换行、大小写、空格变化都会破坏与存量的逐字比对（围栏审计）；
9. **多场景构造错误**：同序列必须同删模式 3/5 且删除条件不同，否则不是场景分组；
10. **数字列形态**：删除模式/规则类型/执行序列在真实导出中为文本单元格（`"5"` 而非 `5`），
    解析器两种都兼容，但与真实导出对齐建议文本；
11. **来源字段名称只填 `s.字段` 形态**（如 `s.cust_id`）——`s` 是平台标准别名，
    **与该规则 SQL 里的表别名无关**（SQL 里叫 `a`/`c`/`t`，登记列仍是 `s.`）；
    无源列可指（如 `COUNT(1)` 这类无源表达式）则**留空**——不要填表达式（`SUM(t.balance)`）、
    裸字段名（`balance`）或跟 SQL 别名走（`t.cust_id`），真实制品里不出现这三种形态。
