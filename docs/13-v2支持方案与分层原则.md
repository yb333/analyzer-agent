# 13 · v2 支持方案与分层原则（编排合入对接的己方实施设计）

> 目标读者：analyzer 侧维护会话。本文收敛 2026-10-14 基于 12 章 v2 需求的三轮架构讨论：
> 需求定位、目标分层、落地耦合诊断、设计守则与波次计划。**是波 1a（结构波）的开工依据**，
> 亦是下次对接（12 章 §五议题）的己方材料。

---

## 一、定位：v2 是消费场景之一，不是架构驱动因素

12 章 v2 需求（编排合入 + v1.2 字段扩充）只是解析能力的**一个消费场景**。评估任何新需求的
第一问是：这个改动是**输入源增强 / 引擎能力**（进核心，所有场景受益），还是**某契约的投影
细节**（留薄适配层，如 baseline_export）？

按此归属，v2 拆出的四件事里三件半是核心能力：

| v2 改动 | 归属 | 说明 |
|---|---|---|
| LTS excel 读取器 | 数据层新输入源 | 兑现 architecture.md §11「LTS 调度展示 ⏸ 待启动」的既有规划，v2 只是第一个消费方 |
| DQ excel 读取器 | 数据层新输入源 | 文档化（说明书质量段）、影响分析（DQ 命中风险标注）、契约导出三场景同候 |
| DDL 物理属性提取 | 引擎层 build_table_catalog 增强 | 分布键变更=重分布成本，对影响分析是高严重度信号 |
| manifest 入口 | 数据层通用装配机制（半个） | 「一次描述 N 个源」对人/批量/agent 是同一机制；manifest 内契约语义（输出指向等）属场景适配 |
| v1.2 schema 字段、DQ 三态空值口径、编排失败语义 | baseline_export 投影层 | 保持薄 |

## 二、目标分层与四条设计纪律

```
输入装配层（通用，待建 = inputs.py）—— manifest / --input，把 N 种源装配成 AssetInputs
  术加 excel ✅ · 代码仓 yml ✅ · DDL 文件 ✅
  DDL 物理属性（增强）· LTS excel（新）· DQ excel（新）· 连库导出（新，波3）

引擎层（通用，不动）
  analyze_pipeline / build_table_catalog —— draft = 富中间表示，信息守恒

投影层（每场景一个，薄）
  三视图+sdd（文档化）· impact.xlsx（影响分析）
  · baseline_v1.json（优化契约，v1.2 扩充全部圈在这里）
  · 契约 B spec 草稿（RS 段，未来第四投影——引擎/投影分离天然承接"一次解析多产出"）
```

1. **draft 富于契约，投影只裁剪。** 读取层对输入源尽量多读（DQ excel 的 rule_code、告警
   配置及未来盘点出的任何平台字段全部进 draft），投影按契约版本裁剪。新契约/新消费方出现时
   只加投影不动引擎——"后续场景核心能力已就位"的保证就在这一条。
2. **新源信息按本质归位，不堆进 knowledge。** knowledge（过程视角）已定型不加料；调度/DQ
   配置进 meta 段，物理属性进 table_catalog——draft 按信息本质组织，不按消费方需求组织。
3. **契约纪律永不渗透进引擎。** 「dm=6 必供 merge_on 否则 fail loud」「dq 声明无输出 `[]`」
   这类语义只存在于投影与校验层（baseline_export），引擎/装配层不知道任何契约版本。
4. **三态语义通用化。** provided / declared_absent / absent（沉默）定义在装配层——对文档化
   场景同样成立（"本资产无 DQ 规则" ≠ "未提供 DQ"），baseline 投影只翻译成自己的空值口径。

## 三、落地耦合现状诊断（2026-10-14 代码事实）

> architecture.md 的三层划分是对的，但落地缺了两个承重结构，耦合都从缺口长出来。以下为
> 代码证据，行号为当日快照。

**证据 1：analyzer.main 是全场景流水线，装配策略没有归属。** analyzer.py 名义上「数据读取
+ CLI」，实际 2536 行中 main + main_chain 占约 950 行。「发现 LTS → 注入 meta」这类装配策略
住在流程代码里（analyzer.py:1802-1804 注释自述"main 发现，注入 meta"模式）；LTS 约 350 行、
DQ 约 110 行、I 视图约 150 行的发现函数全住在 analyzer.py。每加一个源就要改 main——这是
耦合的生成机制，照旧写 DQ/LTS excel 与 manifest 就是重复它。

**证据 2：main 知道契约场景存在。** baseline_v1 的 provenance 组装（analyzer.py:1844-1879，
每种源一段 for 循环）与 export_ctx 手工拼装写在 main 里——数据层流程里出现优化场景的契约
语义；新源进来该段还会再膨胀。

**证据 3：knowledge.meta 是注入口杂物袋。** engine 放 `_timings`，main 注入 `asset_info` /
`schedule` / `dq_rules`，各场景对 draft 字段的理解靠注释约定。这正是 v1.7 分叉的根源
（viewmodel.py 头部自述：字段血缘穿透曾有 4 套实现、源表清单 3 个口径）。

**证据 4：重叠已发生且在扩散。**

| 重叠 | 位置 | 状态 |
|---|---|---|
| excel 读取三件套 `_safe_str/_find_col/_get_val` | analyzer.py:143 与 impact_analyzer.py:152 各一份 | 已复制 2 份，DQ/LTS excel 读取器将是第 3 个消费者 |
| CTE 物理穿透 | engine（权威）+ viewmodel.resolve_physical_sources（回退，viewmodel.py:180） | 两套并存，靠优先级拼合 |
| delete_mode→写入标签映射 | viewmodel._DELETE_MODE_LABEL + baseline_export.WRITE_KIND_BY_MODE + engine 标签 | 3 处口径（delete-mode-vs-rule-type 老债） |
| 引擎接口场景参数 | `context_out=engine_ctx if args.export else None`（analyzer.py:1782） | 引擎开始知道消费场景——防线已开一道口子 |

**根因归纳**：① 输入装配层缺位——「选哪些源、从哪读、发现失败怎么办、三态怎么表达、
provenance 记什么」无模块承载，只能散进 main；② 投影可依赖的稳定面无定义权——draft 结构
靠约定不靠定义，投影间共享取数无唯一权威生产点，分叉后靠重构收敛（v1.7），新投影再长新分叉。

## 四、设计：沿装配层切一刀（strangler，先搬不改）

**1. 新建 `inputs.py`——输入装配层，唯一职责「源 → AssetInputs」。**

```
AssetInputs = {
  rules / target_fields / group_vars   # 术加 excel | yml（现有 read_excel/read_yml 迁移包装）
  schedule                              # LTS excel(新) | LTS yml 发现(平移入) | 无
  dq: DqInputs                          # provided(list) | declared_absent | absent
  table_catalog                         # DDL 文件(含新物理属性) | 连库(波3)
  provenance[]                          # 装配时自动记录，v1.2 含 sheet
}
```

- 存量 LTS/DQ/I 视图发现函数从 analyzer.py **平移**进来（analyzer 留 re-export，仓库有
  engine 抽离的零回归先例），行为不变、所有权归位；
- read_dq_excel / read_lts_excel 为新 loader，**与 yml 解析产出同构 dict**（loader 接口
  契约）——装配层按 manifest/发现规则选源，投影层永远不知道源是 yml 还是 excel；
- excel 三件套收进公共小模块（第 3 份复制即将发生，现在收成本最低）；
- main 瘦身为：装配 AssetInputs → 引擎 → draft → 投影；baseline 的 provenance/ctx 组装挪进
  装配层，main 不再出现 baseline_v1 字样。

**2. 三条防再耦合守则（随波 1a 写进 architecture.md §2，与 v1.7 教训并列）：**

- **单一权威生产点**：一条信息只允许一处生产——物理属性只在 engine 的 table_catalog、
  穿透只在 engine、标签映射只定义一次（顺带治 3 处 delete-mode 标签老债）。投影只裁剪，
  禁止碰原始文本。
- **引擎不知道场景**：`context_out` 始终导出、由装配层持有、投影按需消费——关掉
  `if args.export` 这道口子。引擎接口只描述「要什么」，不描述「谁在用」。
- **注入有主**：schedule/dq_rules 等注入 meta 的动作移到装配层显式函数；meta 每个 key 的
  归属写进契约注释。draft 落盘结构不动（view_generator/batch/impact 均在消费），变的只是
  注入逻辑的所有者——行为零变。

**3. 这次明确不做（防矫枉过正）：**

- 不合并 viewmodel 与 baseline_export——两个投影家族各守其位，跨家族只共享权威生产点，
  等第三个契约家族出现再评估提公共层；
- 不动 asset_report 的 build_report_data，不动 impact_analyzer 的变更清单读取（专属输入）；
- 不全量 manifest 化——`--input` 旧路径内部翻译成隐式装配，外部行为不变。

## 五、新功能落点表

| 改动 | 落点 | 防耦合措施 |
|---|---|---|
| LTS/DQ excel 读取器 | inputs.py 新 loader | 与 yml 解析产出同构；不进 analyzer.py |
| 存量 LTS/DQ/I 视图发现 | 平移入 inputs.py | 先搬不改 + re-export，零回归 |
| DDL 物理属性 | engine.build_table_catalog 唯一生产（TableDef 加 table_props，FieldDef 加 is_distribute_key 等） | 投影层禁止二次解析 |
| manifest + 三态 | inputs.py 装配接口 | 三态是装配层通用语义 |
| v1.2 字段（tables[].table_props / dq_rules[].rule_code+告警配置 / provenance[].sheet） | baseline_export 投影裁剪 | 消费 catalog/provenance，不自己组装 |
| excel 工具三件套 | 公共小模块 | 消第 3 份复制 |

v1.2 延续纯增量先例：只加可选字段，复验 v1.1 产物通过 v1.2 schema；契约文档 §四信息守恒
对账表随 v1.2 同步更新（DQ/LTS excel 每列逐项归档去向），这本身就是对「一次产全」的证明。

## 六、对接议题回应口径（12 章 §五，下次对接过一遍）

1. **DDL 从库导出**：能做。GaussDB/DWS 分布键在 `pgxc_class`、分区在 `pg_partition`、列
   结构走 information_schema。架构上即数据层新 loader（波 3）；前置条件=内网连通 + 只读
   账号 + 凭据管理约定。
2. **一次调用产 baseline_v1 + spec 草稿（契约 B）**：可行，架构零改造——解析一次 → 多投影，
   generate_sdd 已是现成第三投影，契约 B 格式定稿后挂第四投影，互不牵连。
3. **三项扩充字段逆向可得性**：tables 物理属性——DDL 在手即可得，缺则 null+warning；
   dq rule_code/告警配置——excel 读取层直接可得（等模板）；provenance sheet——可得。
4. **DQ excel 字段盘点**：我方提供 excel 模板样例后按对账表逐列归档（见波 1b 依赖）。
5. **安装名/位置**：skill 名 = 目录名 = `dws-pipeline-analyzer`；install.py 装至全局
   `~/.config/opencode/skill/dws-pipeline-analyzer` 或项目级 `.opencode/skill/`，
   dws-reverser 指针按此解析。

另建议对接时明确：`declared_absent`（声明无 DQ）时 `dq_rules` 为 `[]` 而非 `null`，
语义写死进 v1.2 契约。

## 七、波次计划

| 波 | 内容 | 依赖 | 防回归手段 |
|---|---|---|---|
| **1a 结构波**（先行） | inputs.py 骨架 + 存量发现函数平移 + excel 三件套收拢 + context_out 去场景化 + architecture.md 分层原则/守则固化 | 无，可立即开工 | 纯移动零行为变；217 测试 + 四视图 golden 快照 |
| **1b 能力波** | DDL 物理属性（engine）+ DQ/LTS excel loader | excel 模板（用户提供，已确认会提供） | 新 loader 同构性测试（同资产 yml/excel 双源产出对齐） |
| **2 契约波** | schema bump 1.2 + baseline_export 投影扩充 + 契约文档对账表 + fixtures（analyzer 仓先行，按 12 章 §六协议） | 波 1b | v1.1 产物向后兼容复验 |
| **3 对接波** | manifest 全量装配 + 精确输出路径 + 命令文档编排失败语义（fail loud 错误清单原样退回，由消费侧流程决定补数） | 波 2 | 编排模式端到端 fixture |
| 后续另排 | 连库 DDL 导出 · 契约 B 第四投影 | 消费方节奏 | — |

顺序原则：先结构后功能——功能写完再改结构，就是 v1.7 那次重构的剧本重演。

## 八、多场景受益矩阵（通用性的验收标准）

| 新能力 | 文档化 /analyze | 影响分析 /impact | 契约导出 /export-baseline |
|---|---|---|---|
| LTS excel 源 | 说明书展示调度配置（§11 兑现） | 调度类型辅助风险判定 | schedule.params（回刷地基） |
| DQ excel 源 | 说明书质量段展示存量 DQ | 源变更命中 DQ check SQL → 风险标注 | dq_rules 完整化（v1.2） |
| DDL 物理属性 | 表结构完整性 | 分布键变更=高严重度信号 | tables[].table_props（v1.2） |
| manifest 装配 | 多文件一次喂入 | 变更清单+制品一次喂入 | 编排合入（v2） |
| provenance.sheet | 溯源增强 | 溯源增强 | patch 底本定位（v1.2） |

每个新能力合入时对照本矩阵验收：至少两个场景可消费才算"核心能力"，只有单场景消费的
回投影层（例如 write_plan 专属结构）不算。
