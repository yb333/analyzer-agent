# facts 服务使用说明（asset_facts 事实包调用指南）

> 给：需要调用逆向服务的 agent 开发者与流程维护（dws-reverser 及后续消费者）。
> 本文是 facts 服务的完整调用手册——照着做即可，无需了解服务内部实现。
> 产物字段的权威定义见 `docs/asset_facts-契约.md`。

---

## 一、服务是什么

**输入**一个制品目录 + 一个输出路径，**输出**一份存量资产物理事实包（asset_facts.json）。

```
制品目录 ──> facts 服务 ──> asset_facts.json（已过生产方权威 schema 校验）
```

- 制品类型自动识别（excel 按内容指纹、.sql/.ddl 按后缀），**调用方不指认任何文件**
- 目录混放非制品文件（mapping / 说明文档 / 需求单等）不影响运行，服务会逐个登记进
  产物 warnings 供人工复核
- 一次调用一次交卷，没有会话、没有二次调用

## 二、安装

```bash
./install.sh        # macOS/Linux；Windows 用 install.bat；--local 装项目级
```

- skill 名：`dws-pipeline-analyzer`（agent 的 skill 指针按此名解析）
- 环境：Python 3.10+；依赖（openpyxl / sqlglot / pyyaml / jsonschema）随 skill 自检提示，
  消费方无需代装

## 三、调用

```bash
python {skill_dir}/run.py facts --dir <制品目录> --output <asset_facts.json 绝对路径>
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--dir` | 是 | 制品目录（该资产的全部原始制品，见 §八） |
| `--output` | 是 | 产物落盘路径（父目录自动创建） |

## 四、退出码

| 退出码 | 含义 | 标准输出 / 错误输出 | 调用方动作 |
|---|---|---|---|
| **0** | 成功 | stdout 两行：`{格式}: {产物绝对路径}`（格式=`asset_facts` 或 `ts_draft`，随 --format）+ **`self_check: {结论}`** | 按行前缀解析定位；按 self_check 结论分流（见下表） |
| **1** | 制品/数据问题 | stderr 逐条可行动错误清单；产物不落盘 | 错误清单原样上报流程：向人要料或退回。禁止重试、代填、修改制品绕过 |
| **2** | 调用参数错误 | argparse 报错 | 核对 `--dir` / `--output` 后重调一次 |

**`self_check` 三态**（asset_facts 在产物顶层、ts_draft 在 `_reverse.self_check`；stdout 结论行同步打印；三态均 exit 0、产物照常落盘）：

| 结论 | 语义 | 调用方动作 |
|---|---|---|
| `pass` | 干净或无 warnings | 直接进审核对账 |
| `pass_with_noise` | 仅噪音级差异（登记滞后类常态） | 对账过 → 建档，清单进闸口材料披露 |
| `review` | 存在结构级矛盾（料可能给错/资产级对不上） | 审核动作拦下 → 人审（换料重跑 / 显式放行）——**待审不是失败，不要当 exit 1 处理** |

## 五、错误清单与处理

stderr 每条错误都指明"哪个文件、什么问题"。常见特征与对应动作：

| 错误特征 | 原因 | 动作 |
|---|---|---|
| `缺必需料：目录中未识别出术加制品包 excel` | 目录里没有含 RULE + TargetFields sheet 的 excel | 向人要该资产的术加制品包（执行任务导出 excel） |
| `多义：[a.xlsx, b.xlsx]` | 同型制品多个 | 请人确认保留哪个，或分开目录重新调用 |
| `DQ 制品无有效规则行` | 识别出 DQ 制品但主 sheet 没有规则数据 | 核对 DQ 制品导出是否完整 |
| `制品目录不存在` | `--dir` 路径错误 | 核对路径 |
| `[asset_facts] 导出失败` + 违规清单 | 契约校验不过（如 dm=6 的 merge_on 缺失） | 按清单向人要对应配置，补进源制品后重调 |

## 六、产物内容速览

产物 `version` 当前为 **1.4**。各段用途：

| 段 | 用途 |
|---|---|
| `self_check` | 自检结论三态（verdict + 两级计数），交付门分流依据 |
| `rules[]` | 每规则的 SQL 原文（逐字保真，比对锚点）、写入方式（write_plan）、源表清单 |
| `tables[]` | 表与字段；`table_props` 为 DDL 物理属性（分布键/分区/存储参数），`fields[].is_distribute_key` 标记分布键列 |
| `lineage[]` | 字段血缘（raw_expr 逐字），围栏比对锚点 |
| `schedule` | 调度任务与参数（增量变量=回刷地基）；未检出 LTS 时为 null 并在 warnings 披露 |
| `dq_rules[]` | 存量 DQ 规则（含平台规则编码 rule_number 与 target_schema）。**两态**：检出=列表；未检出=`[]` 并在 warnings 披露 |
| `provenance[]` | 每个制品的定位（路径；excel 制品附 sheet 清单），patch 底本回查用 |
| `warnings[]` | 全部"拿不到/对不上"的事实显式化：交叉验证差异 + 分拣披露 + **制品间一致性交叉**（DQ 目标表 / DDL 覆盖与重复 / LTS 组码）。每条带 `severity`（`structural` 结构级置顶 / `noise` 噪音级折叠，分级口径=生产方）。供报告、存档与闸口人工复核 |

### ts_draft（v2）产物速览

`--format ts_draft` 产出 ts.json 形态的**草稿**（version `2.0`）——消费方审核后原样复制
建档，零解析零变换。对齐靶 = 消费方正向设计链路产出的 ts 形态；进门验 = 消费方权威
schema（本服务 vendor，交卷前已过）。

| 段 | 内容 | 处理方式 |
|---|---|---|
| `meta` | target（f_table/i_view 含 DDL 注释）、dq_required、load_strategy（**本服务标准枚举**）、field_count（实计数）、source_tables（SQL 实际别名）、schedule 全段（cron/schedule_type/exec_params/lts_params/tasks f·view·dq 含 upstream） | 恢复 |
| `meta.grain` / `meta.business_key` | `""` / `[]` | **判断位留空**（制品无显式表达；business_key 待 dq_pk_check 口径定稿后可带 provenance 回填） |
| `tables` | 规则产出表 → 三键字段（target_field/field_type/field_comment）+ 物理属性（distribution_key/distribute_type/partition/storage/logical_group） | 恢复；business_key `[]` / build_mode `""` 留空 |
| `rules` | rule_name/exec_sequence/target_table/**query_sql（逐字保真，v2.1 必填——etl 底稿/围栏基准）**/load_mode（write_plan 词表译，词表外 `""`）/write_condition/target_role/reads/produces_for/filter（WHERE 原文）/source_tables+joins（实际别名）/**fields 三桶**（direct 串 `alias.col AS target` 逐字带 AS；assign 常量；processed logic=口径原文 + refs=完整血缘） | 恢复 |
| `rules.*` 判断位 | design_intent/step_type `""`、incremental/grain/derived_fields/dedup_strategy `{}`、join_safety `[]` | 留空（设计判断归 designer） |
| `data_flow` | tables 节点 / dependencies（规则读写拓扑）/ schedule_groups | 派生 |
| `_baseline` | source=`reverse` + provenance（与 asset_facts 同形） | 恢复 |
| `_reverse` | self_check / warnings（severity 两级，含五类交叉）/ write_plan 原文 / schedule_evidence（LTS 原文、tskdep 依赖原文）/ evidence.business_key（merge_on 旁证） | 审核材料（下划线键，围栏/UT 忽略） |
| 不产 | `design` / `init` / `dq_rules` | design·init 归设计判断（init 若有独立制品包，待需求方明确形态后迭代）；DQ 规则本体随 asset_facts 出生证明 |

两点约定：**审计列存量是啥就是啥**（不补造标准审计列）；**未匹配的 LTS 上游依赖不进本体**
（进 `_reverse.warnings` 披露 + `schedule_evidence` 原文，人确认）。逐键映射与原料来源见
`docs/16-ts草稿映射矩阵.md`（联调对账依据）。

与 asset_facts 的关系：**同一次解析、同一条链路、同一份 warnings**，只在投影层分叉——
两种产物的内容一致性由同源保证。双支持期内两格式并行可用，切换节奏由消费方定。

## 七、agent 岗位提示词模板

以下内容可直接嵌入 dws-reverser 岗位定义，即为本服务的全部调用知识：

```
当任务需要逆向存量资产（产出 asset_facts 事实包）时，执行一次调用：

python {skill安装路径}/run.py facts --dir {制品目录} --output {产物绝对路径} [--format ts_draft]

--format 省略=asset_facts（v1 物理事实包）；需要 ts 草稿（直接建档形态）时加 --format ts_draft。

判定与动作：
- exit 0：从 stdout 找以 "asset_facts: " 或 "ts_draft: " 开头的一行（随 --format），取其后路径即产物
  （已过生产方权威 schema 校验）。一次调用一次交卷，不做第二次调用。
- exit 1：制品/数据问题。把 stderr 错误清单原样上报流程（要料/退回），
  禁止：重试、代填数据、自行修改制品、构造其他输入绕过。
- exit 2：参数错误。核对 --dir/--output 后重新调用一次。

不构造 manifest 或任何清单结构——制品类型由服务自动识别。
无法识别的文件不会阻断（会进产物 warnings），无需预先清理目录。
```

## 八、制品目录该放什么

| 制品 | 必需性 | 形态 | 说明 |
|---|---|---|---|
| 术加制品包 | **必需** | excel（执行任务导出） | 唯一缺了会整体失败的料；识别特征 = 含 RULE + TargetFields sheet |
| LTS 调度任务 | 增量资产应有 | excel（平台导出） | 增量变量还原的回刷地基；ts_draft 的 schedule 全段（cron/tasks/upstream 依赖）由它恢复；缺了不阻断，warnings 会披露 |
| DQ 制品 | 可选 | excel（平台导出） | 检出即收录；未检出 = `dq_rules: []` + 披露 |
| DDL | 可选 | `.sql` / `.ddl` 文件 | 后缀即型自动收录；缺则 table_props=null、字段类型由消费方查库回填 |

文件名任意、混放无关文件不阻断；`.txt` 不会被当作 DDL（歧义后缀不猜）。
yml 代码仓形态的资产不走 facts 入口（见 §九）。

## 九、备用形态：--input（人工通道）

人工逐件指认输入，或分析 yml 代码仓资产时使用：

```bash
python run.py analyzer --input {术加.xlsx 或 规则组目录} --output ./output/ \
    [--ddl-dir D] [--lts {LTS excel}] [--dq {DQ excel}] \
    --export asset_facts [--platform-generation 1.0]
```

产物：`{output}/{规则组英文名}/asset_facts.json`，stdout 定位行约定同 facts。
yml 场景自动发现 DDL / LTS / DQ / I 视图。

## 十、版本与支持

- 产物契约版本当前 **1.4**（交付门：self_check 三态 + severity 两级 + 一致性交叉）；
  schema 权威文件 `dws-pipeline-analyzer/schemas/asset_facts.schema.json`
- 契约演进节奏：生产方先行（schema + 文档 + fixtures + version bump）→ 消费方跟随
  （vendor + 校验器适配 + 契约测试绿）→ 同波各自同步内网。消费方运行时先对 `version`
  字段，不支持即 fail loud
- **ts_draft（v2）契约权威在消费方、本服务 vendor**（方向与 asset_facts 相反）：本服务
  vendor 了 `ts_draft_v2.schema.json` / `ts_draft_v2.example.json` / `ts_sample_forward.json` /
  `ts-template.json` 四件并以指纹联锁守护。**消费方变更任一文件须通知本服务 re-vendor**
  （形态演进=契约波次：消费方先行 → 本服务 re-vendor + 投影适配 + 测试绿 → 同波同步内网）
- 两处口径以本服务为准、消费方遵循：`meta.load_strategy.strategy` 枚举；warnings
  严重度分级
- 对接沟通：任何字段需求 / 新制品形态 / 错误清单不清晰，提生产方仓 issue 或对接会

## FAQ

**Q：产物校验谁来保证？** 生产方交卷前已过权威 schema 全绿（校验不过不落盘）；
消费方入料仍应跑自己的校验链（版本 → schema → 内部一致性 → 资产对账）。

**Q：制品文件名很乱能识别吗？** 能。判型只看内容（sheet 结构）与后缀，与文件名无关。

**Q：目录里有两个同型 excel？** 服务会报"多义"失败——请人确认保留哪个。

**Q：可以只解析不出契约吗？** 可以，`--input` 不带 `--export` 走文档化分析，
与契约导出共用同一解析引擎。
